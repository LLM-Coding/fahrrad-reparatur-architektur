== Kontextabgrenzung

Das Kontextdiagramm war Eberhards erster Schritt. "Ich habe dadurch ein besseres Bild bekommen, was ich bauen soll und mit wem ich interagieren muss, insbesondere welche Verantwortung ich habe und welche Schnittstellen" (Folge 111, 26:03). Er trennt fachlichen und technischen Kontext in zwei Diagramme (27:51, 28:22). Beide zeigen dieselben drei Akteure und sieben externen Systeme (Miro-Board Seiten 2 und 3).

Das Reparatur-System trägt die Verantwortung für alles rund um die Reparatur: Termine, Plan, Protokoll, Bestand an Ersatzteilen und Werkzeug (<<09_architecture_decisions.adoc#adr-006,ADR-006>>) und die Bezahlung. Es besitzt keine eigene Nutzerverwaltung und keine eigene Zahlungsabwicklung; beides liegt bei Nachbarsystemen. Der Großhändler für Ersatzteile und Werkzeug ist kein externes System im Kontext, sondern Empfänger einer Bestellung (Board Seite 7).

NOTE: Offen: Ob die Bestellung beim Großhändler über eine Schnittstelle oder manuell läuft, zeigt das Board nicht. Quelle: Transkript Folge 112/113 ausstehend.

[cols="2,3,3" options="header"]
|===
|Externes System |Schnittstelle (Board Seite 3) |Erläuterung

|Webshop
|Umleitung von URLs (`/reparatur`)
|Der Webshop leitet den Pfad `/reparatur` an das Reparatur-System weiter. So bleibt das System in derselben Domain und die Same-Origin-Policy lässt den Cookie durch (<<09_architecture_decisions.adoc#adr-002,ADR-002>>).

|Webshop User Database
|JWT als Cookie, REST
|Der Webshop setzt nach dem Login einen JWT als Cookie. Das Reparatur-System liest daraus die Identität und fragt Adresse und Zahlungsart per REST ab (<<09_architecture_decisions.adoc#adr-001,ADR-001>>).

|Kasse
|REST
|Protokoll "meinetwegen REST" (30:52); die Details sind bewusst offen gelassen.

|Online Payment Service
|REST und UI-Integration (Redirect-Button)
|Backend-Integration per REST für den Buchungsstatus, dazu ein Button, der die Kund:in zum Dienst umleitet (<<09_architecture_decisions.adoc#adr-004,ADR-004>>).

|Rechnungswesen
|REST
|Übergabe der Rechnungselemente; Protokoll als Default gewählt.

|EMail System
|REST
|Zugekaufter Dienst, etwa AWS Simple Email Service (31:02).

|SMS Versand
|REST
|Kanal vorgesehen, nicht entschieden (<<09_architecture_decisions.adoc#adr-007,ADR-007>>).
|===

Die fachlichen Schnittstellen bilden sich so auf die technischen ab: Alles, was Akteure tun, läuft über den Webbrowser und den vom Webshop umgeleiteten Pfad `/reparatur`. Die Identität der Kund:in kommt nicht aus einem eigenen Login, sondern aus dem JWT-Cookie des Webshops; die Nutzerdaten dazu liefert die User Database per REST. Bezahlung im Laden fließt als Preis per REST an die Kasse, Online-Bezahlung als REST-Aufruf plus UI-Redirect an den Payment Service. Rechnungselemente und Benachrichtigungen verlassen das System ausschließlich als ausgehende REST-Aufrufe. Für alle Protokolle außer der Webshop-Anbindung gilt REST als Default; Eberhard hat gRPC oder anderes ausdrücklich nicht bewertet (29:53, 30:04).

NOTE: Offen: Hosting der externen Systeme (Webshop, User Database) ist bewusst nicht erfasst (35:36). Ob Kasse und Rechnungswesen aus der Cloud erreichbar sind, bleibt eine offene Frage auf dem Board (Seiten 10 und 11). Quelle: Transkript Folge 112/113 ausstehend.
